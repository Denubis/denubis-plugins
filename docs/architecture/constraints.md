# Quality Constraints

Measurable limits on the behaviour of `brian-ed3d-plugins` and the disciplines its plugins encode. Each constraint has a requirement and a verification method.

## Repository Integrity

| Constraint | Requirement | Verification |
|------------|-------------|-------------|
| Version sync | Every change to a plugin's `plugin.json` version must appear in the matching entry in `.claude-plugin/marketplace.json` AND a `CHANGELOG.md` entry must be added in the same commit. | Manual review at commit time; codified in `CLAUDE.md` (`b9bed28`). Automated test: see top-level `tests/` (referenced by `pyproject.toml`'s testpaths). |
| Per-plugin scope | Each plugin holds responsibility for one concern. Hook-only plugins ship only hooks; skill bundles ship only skills/agents/commands. Mixed plugins (notably `denubis-plan-and-execute`) are exceptions justified by their orchestration role. | Directory-listing review per release. |
| HALT on anomaly | When repo state appears mid-refactor, contradictory, or sideways — including mixed conventions, orphaned files, contradictions between docs, or reviewer findings at any level — halt and discuss rather than work around it. | Codified in `CLAUDE.md` (`b9bed28`). Surfaced in the `using-plan-and-execute` skill body and reinforced by reviewer agents at phase transitions. |
| Version bumps after the feature works | Do not bump `plugin.json` / `marketplace.json` / `CHANGELOG.md` on every WIP commit — bump once when the feature is verified working. | Per the user's standing feedback; observable via `git log -- <plugin>/.claude-plugin/plugin.json`. |
| Honouring prior architectural decisions | When the user signals "don't we already…" or "I thought we…", that signal is authoritative; research-agent outputs and prior session work are inputs, not conclusions. | Per the user's standing feedback; reinforced by `proleptic-challenger` at phase transitions. |

## Tool-Call Discipline (enforced by hooks)

| Constraint | Requirement | Verification |
|------------|-------------|-------------|
| Fork isolation | `gh` CLI commands targeting any repo other than the user's fork are denied. The allowed repo is set via `ALLOWED_GH_REPO` or inferred from `git remote get-url origin`. | `denubis-hook-gh-fork-guard`'s `gh-fork-guard.py` (`f62e8a6`) running under the `pretooluse-bash` dispatcher at priority 10. |
| Token economy | Commands matching the RTK rewrite catalogue (git, gh, file ops, JS/TS tooling, Docker, Python tooling, etc.) are transparently rewritten to `rtk <cmd>` to reduce token output. | `denubis-hook-rtk-rewrite`'s `pretooluse-bash.sh` (`c580ff0`) running under the dispatcher at priority 50. |
| Banned-pattern writes | File writes/edits that match patterns the user has banned (e2e JS injection, `create_all`, migration edits, debug statements, easy-mode shortcuts, spec weakening) are denied or warned at `PreToolUse:Write|Edit`. | `denubis-plan-and-execute/hooks/code-quality-guard.py` (`9bac7ed`) with 5s timeout. |
| Stop-time shortcut detection | When the assistant's last message contains a shortcut phrase (e.g. "let me try a different approach", "for simplicity"), the `Stop` hook blocks the turn so the user can interrogate before the model abandons an approach. | `denubis-hook-shortcut-detection`'s `shortcut-detector.py` (`22d2148`), keyed per-session via a lockfile under `/tmp/shortcut-detector/`. |

## Process Discipline (encoded by skills)

| Constraint | Requirement | Verification |
|------------|-------------|-------------|
| Brainstorming before coding | New features go through `denubis-plan-and-execute:starting-a-design-plan` (brainstorm → clarify → write → proleptic-challenge → architecture-update) before any code change. | Skill bodies; reinforced by `using-plan-and-execute` injected at every `SessionStart`. |
| TDD on implementation | Every feature/bugfix writes a test first (red-green-refactor); never delete failing tests to pass. | `coding-tdd` skill body; `task-implementor` agent enforces TDD. |
| Multi-agent review | Major work passes through `code-reviewer`, `coherence-reviewer`, `critical-peer-review`, and `test-analyst` agents before merge. | Skill `requesting-code-review` + the agent set in `denubis-plan-and-execute/agents/`. |
| Single bundled review pass | At most one fix-then-re-review cycle per phase before halting for user direction. | `requesting-code-review` skill body (per commit `9f7fab9` — *"bound code-review loop to one cycle, then HALT"*). |
| Plugin manifest description shape | Every plugin's `plugin.json` description is QA-tested for shape (length, content). | Top-level `tests/` directory test (per commit `8498518` — *"enforce and apply skill description shape"*). |

## Workspace Discipline

| Constraint | Requirement | Verification |
|------------|-------------|-------------|
| Workspace test collection | A single `uv run pytest -q` from the worktree root must collect every test across root + all plugin packages. Each plugin keeps its own `pyproject.toml`; the workspace declaration in root `pyproject.toml` shares the `.venv`. No plugin `tests/__init__.py` may exist (it makes pytest treat the dir as a package requiring `sys.path` setup that defeats workspace collection). | 615 baseline → 618 after Phase 1 tests → 619 after M1 cascade test. Source: `pyproject.toml::tool.uv.workspace`. |

## Crash-Recovery Discipline (implemented through Phase 6)

These constraints govern the `crash-recovery` plugin. Phase 1 implements the database schema and `init` subcommand; Phase 2 the JSONL tail parser and classifier; Phase 3 the liveness file reader, boot-id read, PID-alive check, and UUID correlation; Phase 4 the end-to-end `scan` orchestration (filesystem walk → classify → single-transaction upsert → orphan sweep) and the `crash-recovery scan` CLI subcommand; Phase 5 the `crash_recovery.render` module, the `render` / `triage` / `regenerate` CLI subcommands, and the markdown contract. The constraints below are enforced by code as of Phase 5 with remaining phases cited where enforcement is deferred.

| Constraint | Requirement | Verification |
|------------|-------------|-------------|
| Deterministic classification | Given a fixed SQLite database state, `crash-recovery render` produces byte-identical markdown output. No LLM judgement participates in classification — every classification value is produced by a parametrised rule table. | CHECK constraint on `classification` enforced by `db.py::CLASSIFICATION_HISTORY_DDL`; invalid values rejected: `tests/test_init.py::TestConstraints::test_classification_history_classification_check_rejects_invalid_value`. Phase 2's `classify()` first-match RULES table verified by `tests/test_classify.py`. Render byte-stability implemented in Phase 5: `tests/test_render.py::test_render_is_byte_identical_across_calls` and three snapshot tests (`test_render_matches_snapshot[empty|mixed|all_concluded]`). |
| Idempotent scan | Repeated `crash-recovery scan` invocations against an unchanged filesystem state produce identical DB rows (`last_scanned` timestamp aside). `first_seen` is preserved across upserts; no duplicate `classification_history` rows accumulate (M4 write-side dedup, 2026-05-17). | Schema idempotency verified by `tests/test_init.py::TestInitIdempotent::test_init_is_idempotent`. Scan-level idempotency: `tests/test_scan.py::test_scan_is_idempotent`. History dedup pinned by `tests/test_scan.py::test_classification_history_skips_append_when_unchanged` and the inverse `test_classification_history_appends_when_classification_changes`. |
| Boot-aware liveness | A liveness file whose `boot_id` does not match `/proc/sys/kernel/random/boot_id` is classified as a casualty regardless of whether its PID is currently alive. This prevents post-reboot PID-recycling false positives. | Reader side: `liveness.py::current_boot_id` reads the kernel value; `Liveness.boot_id` exposes the file value. Wired into `_walk_sessions` via `boot_id_current=(liveness.boot_id == current_bid)` (`scan.py`) and consumed by `classify()`'s precedence rule. End-to-end pin: `tests/test_scan.py::test_scan_classifies_boot_mismatch_as_hard_crash_even_if_pid_alive`. Reboot UAT deferred to Phase 8. |
| Liveness file four-key format | A `.live` file must declare `cwd`, `started`, `argv`, `boot_id` as key=value lines; extra unknown keys are tolerated; the filename stem must be a non-negative integer (the wrapper PID). Malformed files raise `ValueError` at the parser and are warning-and-skipped during enumeration. | `liveness.py::read_liveness` parser; `tests/test_liveness.py` pins missing-key, non-numeric-filename, non-int-`started`, extra-key-tolerated, and `=`-in-argv preservation paths. Writer side lands in Phase 8. |
| pid_alive returns bool, never None | `pid_alive(pid)` returns a real `bool` under every reachable code path. `ProcessLookupError` → `False`; `PermissionError` and every other `OSError` subclass → `warnings.warn(UserWarning)` + `False` (the PID has been recycled to a process this user does not own, so the wrapper itself is gone). Nothing propagates. | `liveness.py::pid_alive` single `except OSError` branch. Two symmetric pin-tests in `tests/test_liveness.py`: `test_pid_alive_permission_error_returns_false`, `test_pid_alive_unexpected_oserror_returns_false_with_warning`. Load-bearing on Phase 2's `classify()` boundary check (`pid_alive=None` with `liveness_state.present=True` raises `ValueError`). Recorded after Phase 2 proleptic CA2 (2026-05-16). |
| Lossy-encoding collision safety | `_project_dir_for_cwd` must scan every JSONL in a child directory rather than short-circuiting after the first. Claude Code's encoded-directory naming is lossy (`/` and `.` both collapse to `-`), so two distinct cwds can share one encoded directory. The first JSONL's cwd is NOT authoritative under collision. | `correlate.py::_project_dir_for_cwd` uses `continue` (not `break`) after a non-matching cwd. Pinned by `tests/test_correlate.py::test_project_dir_for_cwd_handles_encoding_collision` (two distinct cwds in one encoded dir; both are findable). An earlier draft's break-out-of-inner-loop optimisation was removed after Phase 3 proleptic CA1 (2026-05-16). |
| Local-filesystem refusal | `crash-recovery scan`, `render`, and `regenerate` refuse to operate on network or union filesystems where `rename(2)` atomicity is not guaranteed (NFS write+rename races, FUSE/sshfs latency, overlayfs union semantics). The tempfile + `os.replace` pattern used by both `scan` (liveness files) and `render` (output file) requires POSIX rename atomicity on a local filesystem. | `liveness.py::assert_local_filesystem` uses `findmnt -no FSTYPE -T <path>` (or `/proc/mounts` fallback) and refuses members of `_REFUSED_FSTYPES_EXACT` ∪ prefixes-of `_REFUSED_FSTYPE_PREFIXES`. Parametrised refusal test in `tests/test_liveness.py::test_assert_local_filesystem_refuses_simulated_nfs`. Invoked by Phase 4's `scan` CLI at entry (`__main__.py::scan`); CLI-level refusal pinned by `tests/test_scan.py::test_scan_cli_refuses_when_run_dir_is_on_network_fs`. Phase 5 extends the guard to `_render_to_file` on `output.parent` (coherence M2); `render` and `regenerate` both inherit the guard via `_render_to_file`. Writer-side liveness guarantee (CA3) deferred to Phase 8. |
| No auto-prune | `crash-recovery prune` only deletes rows when invoked with `--confirm` AND a **four-condition guard** holds: classification is `concluded` AND `user_notes IS NULL` AND `jsonl_path` is no longer on disk AND `classifier_version` matches the current `CLASSIFIER_VERSION` constant (AC7.7). Re-running triage never silently removes entries. | `prune.py::survey` (read-only) + `prune.py::delete_candidates`; tests `tests/test_prune.py::test_prune_dry_run_is_read_only`, `..._without_confirm_refuses`, `..._confirm_deletes_matching_rows`, `..._preserves_concluded_with_user_note`, `..._preserves_concluded_with_extant_jsonl`, `..._excludes_stale_classifier_version_rows`, `..._confirm_does_not_delete_stale_rows`, `..._cascades_classification_history_deletion`, `..._dry_run_and_confirm_mutually_exclusive`, `..._empty_db`. |
| Classifier version forward-compat | Each scan stamps the current `CLASSIFIER_VERSION` onto every row it touches. When the rule table changes, scan re-classifies version-stale rows (and all orphans per DR10) before render or prune queries see them. Prune therefore always operates against rules currently in force. | Implemented in `scan.py::_orphan_sweep` and `_upsert_session`. Pinned by `tests/test_scan.py::test_scan_reclassifies_stale_classifier_version_rows` (vanished-JSONL path) and `test_scan_reclassifies_stale_row_whose_jsonl_still_exists` (surviving-JSONL path). |
| Single-transaction scan write model | `run_scan` opens one SQLite connection and wraps the entire write block (`_write_scan_run` + per-fact upserts + `_append_history` + `_orphan_sweep`) in a single `with conn:` transaction. WAL mode lets concurrent readers proceed unblocked; concurrent `scan` invocations serialize at the write lock. On any exception the transaction rolls back atomically. Accepted as a design choice at Phase 4 closure (2026-05-17): acceptable for the expected scale (hundreds to low thousands of sessions); see phase_04.md Outstanding. | `scan.py::run_scan` uses `with closing(db.open_db(...)) as conn: with conn:`. Atomicity pinned by `tests/test_scan.py::test_scan_atomic_on_simulated_failure` (mid-loop exception → zero rows in `sessions` AND no `scan_runs` row). Concurrency pinned by `tests/test_scan.py::test_scan_two_concurrent_invocations_do_not_corrupt_db` (two `Popen([..., "scan"])` invocations against the same DB, both exit 0, exactly 2 `scan_runs` rows, exactly 3 `sessions` rows). |
| Empty-cwd guard | A JSONL-only session whose `_first_entry_cwd` returns `""` (corrupted/truncated/missing-cwd-key JSONL) is classified as `IRRECOVERABLE/missing_cwd` rather than written with empty cwd. The row remains visible in triage with a clear reason; Phase 7's `claudew --resume` will skip offering a resume for it. | `scan.py::_classify_fact` short-circuits `not fact.cwd → Classification(IRRECOVERABLE, "missing_cwd")` before any other rule. Pinned by `tests/test_scan.py::test_walk_emits_irrecoverable_missing_cwd_for_unreadable_jsonl`. |
| Deterministic render (Phase 5) | `render(db_path)` returns a byte-stable markdown string. Two calls against the same DB state produce `==` output. Sort order is `last_scanned DESC, uuid ASC` (the uuid tiebreaker prevents non-determinism on same-epoch rows). | `tests/test_render.py::test_render_is_byte_identical_across_calls` AND three snapshot tests: `test_render_matches_snapshot[empty]`, `test_render_matches_snapshot[mixed]`, `test_render_matches_snapshot[all_concluded]`. |
| Reason-partition exhaustiveness (Phase 5) | Every reason emitted by `classify.RULES` plus `ambiguous_match` and `unmatched` belongs to exactly one of (`LIVENESS_REASONS`, `NO_LIVENESS_REASONS`, `JSONL_ONLY_REASONS`). The three sets are pairwise disjoint. Section assignment via `_section_for_row` is total over all reachable reasons. | `tests/test_render.py::test_reason_prefix_partition_is_exhaustive`. |
| Irrecoverable-row resume suppression (Phase 5) | Rows with `classification == "irrecoverable"` render the strikethrough `~~no resume — <reason>~~` form (em-dash U+2014) and NEVER advertise `claudew --resume <uuid>`. The reduced-confidence line is also suppressed. Locks the Phase 4 coherence-review falsification anchor (commit `b79dd05`). | `tests/test_render.py::test_irrecoverable_row_suppresses_resume_command`. |
| Atomic markdown write (Phase 5) | `crash-recovery render` and `regenerate` write the output file via `tempfile.NamedTemporaryFile(dir=output.parent) + os.replace`. The tempfile is created in `output.parent` so the rename stays on the same filesystem. `output.parent` is checked against `assert_local_filesystem` before the write begins; a network or union filesystem exits with code 2. | `__main__.py::_render_to_file`: guard call precedes `mkdir + NamedTemporaryFile`. `tests/test_render.py::test_render_overwrites_user_edits` (atomicity via overwrite). |
| Annotation-preserves-classification (Phase 6 Task 0) | `user_notes IS NOT NULL` causes `_orphan_sweep` to skip the row entirely — no classification flip, no `classifier_version` bump, no `classification_history` append, no `last_scanned` refresh. | `tests/test_scan.py::test_orphan_sweep_preserves_annotated_session_classification` (positive) + `..._reclassifies_unannotated_session` (paired re-pin of AC3.6). |
| Annotation note CRUD fail-loud guard (Phase 6) | `note.py::set_note` and `note.py::clear_note` use `UPDATE ... WHERE uuid = ?` + `rowcount == 0` check, raising `UnknownSessionError` on a typo'd UUID — never silently inserts and never silently no-ops. The CLI maps the error to exit code 2 with a stderr message. | Tests in `tests/test_note.py`. |
| Prune cascade reliance on Phase 1 FK (Phase 6) | `prune.py::delete_candidates` issues a single `DELETE FROM sessions WHERE uuid IN (...)`; the cascade to `classification_history` rows fires inside the same transaction via Phase 1's `FOREIGN KEY (uuid) REFERENCES sessions(uuid) ON DELETE CASCADE` + `PRAGMA foreign_keys = ON` from `db.open_db`. There is NO separate `DELETE FROM classification_history`. | `tests/test_prune.py::test_prune_cascades_classification_history_deletion` pins both the schema and the PRAGMA. |
| CLI exit-code contract (Phase 6) | `crash-recovery` subcommands map exit codes by class — `0` = success; `1` = "no data" (e.g., `history` against a UUID with no `classification_history` rows; `prune` refusal without `--confirm`); `2` = "invalid input or operation refused" (e.g., `note` against an unknown UUID, `--dry-run --confirm` mutually exclusive, platform guard refusing on non-Linux, local-filesystem guard refusing on network mounts). Skill authors and shell scripts should treat exit 1 as "valid invocation, no result" and exit 2 as "invocation rejected, fix the call". | Test docstring `tests/test_history.py:227-241` documents the rationale. |
